## 0. 최종 결론

Golden Look은 보호자가 제공한 실종자 사진과 실종 당시 정보를 바탕으로 **이미지 편집/생성 AI가 실종 당시의 예상 모습을 재현하고 모바일 전단으로 발행·공유하게 하는 서비스**다.

핵심 분기는 업로드 단계의 체크박스 하나다.

- **`얼굴만 나온 사진인가요?` 미체크** → 기존 몸이 보이는 사진을 기반으로 **옷 색 + 옷 형태를 편집**한다.
- **체크** → 얼굴 사진을 기준으로 나이·키·성별·체형·옷 정보를 반영해 **자연스럽게 서 있는 예상 전신/몸통 이미지를 생성**한다.

모든 AI 결과에는 **`AI로 재현한 예상 모습`** 라벨/워터마크를 표시한다. 공개 전단은 팀장 결정에 따라 생성 결과를 중심 이미지로 사용한다.

### 이번 v4에서 폐기된 v3 기준

- Gemini 자연어 옷차림 파싱
- 카테고리별 자연어 입력
- SegFormer + LAB recolor를 핵심 파이프라인으로 사용하는 구조
- 얼굴만 나온 사진은 재업로드해야 한다는 규칙
- 얼굴·몸·옷 형태 생성 금지
- Modal 기반 segmentation 서버를 필수 인프라로 보는 구조

# 1. 문제 정의

보호자가 가진 실종자 사진은 과거 사진일 가능성이 높고, 실종 당일에는 다른 옷을 입고 있을 수 있다. 특히 보호자가 가진 사진이 얼굴 위주의 사진뿐인 경우 시민이 실제 거리에서 보게 될 실종자의 전체 모습을 상상하기 어렵다.

Golden Look은 보호자가 기억하는 정보를 구조화된 입력으로 받고, 원본 사진을 기반으로 **당일 예상 모습을 시각적으로 재현**하여 텍스트만 있는 전단보다 빠르게 이해할 수 있도록 한다.

## 1.1 1차 타깃

- 치매 고령자 실종 보호자
- 긴급한 상황에서 스마트폰으로 빠르게 전단을 만들어야 하는 사용자
- 복잡한 AI 입력보다 큰 버튼/선택형 UI가 필요한 사용자

## 1.2 핵심 가치

> **과거의 사진을, 보호자가 기억하는 실종 당일 정보에 기반한 ‘AI 예상 모습’으로 재현한다.**

# 4. 사용자 입력 데이터

## 4.1 사진 유형

```ts
type PhotoMode = "body_visible" | "face_only";
```

UI는 기술 용어를 쓰지 않고 다음 체크박스로 받는다.

> `얼굴만 나온 사진인가요? (몸이 보이지 않아요)`

- 체크 X → `body_visible`
- 체크 O → `face_only`

판단 책임은 MVP에서는 사용자에게 둔다. 자동 판별은 P0가 아니다.

## 4.2 옷 정보

색은 자유 텍스트가 아니라 `contracts/colors.json`의 20색만 사용한다.

```json
{
  "top": { "status": "known", "color": "blue", "type": "반팔 티셔츠", "brand": null },
  "bottom": { "status": "known", "color": "gray", "type": "면바지", "brand": null },
  "hat": { "status": "none" },
  "shoes": { "status": "unknown" },
  "items": [{ "type": "지팡이", "color": "brown" }]
}
```

### 입력 원칙

- `known`: 사용자가 기억하고 선택한 정보
- `none`: 사용자가 없다고 선택
- `unknown`: 기억 안 남
- 기억 안 나는 부분은 AI 프롬프트에서 **사실로 확정하지 않는다.**

### 얼굴-only에서 옷 종류가 비어 있을 때

상의/하의 종류는 **선택 입력**이다.

종류가 없으면 AI는 다음 제한을 받는다.

- 로고 없는 기본 의상
- 과한 패턴 없음
- 중립적이고 일반적인 형태
- AI가 보완한 종류를 전단 텍스트에 사실 정보로 추가하지 않음

## 4.3 얼굴-only 추가 몸 정보

- 나이
- 키
- 성별: 남 / 여
- 체형: 마른편 / 보통 / 통통한편

몸무게 kg는 받지 않는다.

# 5. AI 재현 정책

## 5.1 body_visible 모드

Gemini 이미지 편집 API에 원본 이미지를 제공한다.

목표:

- 얼굴 정체성 최대한 유지
- 배경 최대한 유지
- 실사 스타일 유지
- 사용자가 지정한 색 반영
- 사용자가 옷 종류를 입력했으면 형태 변경 허용
  - 예: 패딩 → 반팔 티셔츠
- 종류 미입력 시 기존 옷 형태를 우선 유지
- 기억 안 나는 항목은 임의로 강조/추정하지 않음

## 5.2 face_only 모드

Gemini 이미지 생성/편집 API에 얼굴 사진과 몸 정보를 제공한다.

목표:

- 제공된 얼굴 특징을 최대한 유지
- 자연스럽게 서 있는 자세
- 나이/키/성별/체형을 반영한 예상 몸
- 사용자가 입력한 옷 색/종류를 반영
- 미입력 의상 종류는 중립적 기본 의상
- 실사 스타일, 만화/일러스트 금지
- 과도한 액세서리/로고/패턴 생성 금지

## 5.3 결과 표시

결과 이미지에는 반드시 다음 문구를 표시한다.

> **AI로 재현한 예상 모습**

공개 전단에서는 생성 결과 이미지를 메인 이미지로 사용한다. 원본 이미지는 내부 case 데이터와 재생성용 입력으로 보관하며 MVP 공개 전단의 메인 이미지로 병기하지 않는다.

## 5.4 재생성

- 최초 생성 후 `다시 생성` 버튼 제공
- 재생성 최대 **3회**
- 재생성 시 동일 입력을 유지할 수 있고, 사용자는 입력을 수정한 뒤 다시 시도할 수 있다.
- 모델/API 오류는 재생성 횟수에서 차감하지 않는 방향을 권장한다.

# 6. AI 팀 개발 자율성 정책 - 최소 제약

AI 담당자가 구현을 빠르게 실험할 수 있도록 **내부 AI 구현에는 최소한의 제약만 둔다.**

## 6.1 AI 담당자가 사전 승인 없이 변경 가능한 것

- Gemini 이미지 모델 버전
- 향후 다른 이미지 provider로 교체하는 실험
- prompt 구조/system instruction
- 이미지 해상도/압축/후처리
- 생성 품질 검증 로직
- provider SDK 구조
- 캐시/재시도/timeout
- AI 관련 폴더 구조
- 비용/속도 최적화
- 내부 응답 metadata
- 생성/편집 방식을 하나의 adapter로 합치거나 분리하는 구현

현재 baseline provider는 **Gemini Image API**이지만, 더 좋은 방법을 찾으면 AI 담당자가 실험·수정할 수 있다.

## 6.2 반드시 지켜야 하는 최소 Integration Contract

AI 구현 자유보다 아래 6개만 우선한다.

1. 입력의 `photoMode` 의미를 깨지 않는다.
2. 사용자가 선택한 옷/몸 정보를 받을 수 있어야 한다.
3. 최종 성공 시 앱이 표시할 수 있는 이미지 결과를 반환한다.
4. 실패는 사용자 입력 오류와 provider/temporary 오류를 구분할 수 있어야 한다.
5. Secret/API key/원본 이미지 base64/전화번호를 로그에 남기지 않는다.
6. 재생성 최대 3회와 `AI로 재현한 예상 모습` 표시를 우회하지 않는다.

## 6.3 변경 보고 방식

AI 담당자는 구현을 자유롭게 바꾸되 **Integration에 영향이 있으면 반드시 보고**한다.

보고 대상:

- API request/response 필드 변경
- 필요한 환경변수 추가/삭제
- DB/Storage 구조 변경 필요
- Frontend에서 새 입력이 필요
- Provider 변경
- 예상 비용 구조가 크게 변함
- 기존 결과와 호환되지 않는 breaking change

권장 보고 형식:

```text
[AI CHANGE REPORT]
변경: Gemini 모델 A → B
이유: 얼굴 보존 품질 개선
외부 계약 영향: 없음 / 있음
새 환경변수: 없음
Frontend 영향: 없음
Backend 영향: adapter 내부만 변경
비용 영향: 약 +20%
검증: sample 10건 비교
```

### 권한 원칙

- AI 담당자는 Backend의 AI 관련 영역을 사실상 **owner**처럼 수정할 수 있다.
- 외부 계약이 유지되면 사전 승인 없이 작업/PR 가능하다.
- 외부 계약이 깨지는 변경도 feature branch에서 실험은 가능하다.
- 단, **Frontend/DB/API contract를 깨는 변경을 main에 merge하기 전에는 팀에 보고하고 통합 담당과 맞춘다.**

즉, **AI 구현 방법은 자유롭게, 통합 경계는 보고 후 변경**한다.

# 10. 데이터 모델 핵심

`cases`는 최소 다음 정보를 가진다.

- `id`
- `user_id`
- `share_id`
- `photo_mode`
- `appearance`
- `body_profile` (face_only인 경우)
- `original_path`
- `generated_path`
- `generation_attempts`
- `generation_status`
- `name`, `age`, `height_cm`, `missing_at`, `place`, `contact`, `notes`
- `created_at`, `updated_at`, `published_at`

`body_profile` 예:

```json
{
  "gender": "male",
  "bodyType": "slim"
}
```

# 11. API 기준

외부 경로는 통합 비용을 줄이기 위해 단순하게 유지한다.

| Method | Path | 역할 |
|---|---|---|
| POST | `/api/cases` | case + 사진 생성 |
| GET/PATCH/DELETE | `/api/cases/[id]` | 조회 / 사진·입력 수정 / 삭제 |
| POST | `/api/cases/[id]/generate` | Gemini 이미지 생성/편집 |
| POST | `/api/cases/[id]/publish` | 전단 발행 |
| GET | `/api/flyer/[shareId]` | 전단 PNG |

AI 담당자 내부 adapter endpoint/함수 구조는 자유다. 다만 위 앱-facing contract 변경 시 보고한다.

- 결과는 실제 사진이 아니라 `AI로 재현한 예상 모습`으로 명시
- AI가 만든 옷 종류/몸 형태를 사실 정보 텍스트로 자동 확정하지 않음
- 생성 결과는 보호자 확인 후 발행

---

# 13. 성공 지표

- 두 사진 모드 모두 E2E 성공
- 몸 사진: 옷 형태/색 반영 성공률
- 얼굴-only: 얼굴 유사성 주관평가 + 실사성 + 입력 반영률
- 재생성 3회 안에 보호자가 선택 가능한 결과 도달률
- 평균 생성 시간
- 이미지당 비용
- 가입 → 발행까지 완료 시간
- 타 계정 private case 접근 차단 100%

---

# 14. 일정 원칙

1. Auth/ownership과 이미지 AI adapter 계약부터 고정한다.
2. AI 담당자는 병렬로 Gemini 이미지 생성/편집 품질을 실험한다.
3. Frontend는 mock generate response로 먼저 UX를 만든다.
4. AI 내부 구현이 바뀌어도 app-facing contract만 유지하면 통합 일정에 영향이 없도록 한다.
5. 제출 2일 전부터 기능 추가 금지. 품질/통합/배포만 고친다.

# 15. 최종 동결 목록

팀장 승인/보고 없이 깨면 안 되는 것은 최소한으로 제한한다.

- MVP 로그인 및 case ownership
- `photoMode`: body_visible / face_only
- 20색 palette id
- 사용자가 `unknown`으로 둔 정보를 사실로 확정하지 않는 원칙
- 재생성 버튼 최대 3회
- AI 결과 라벨 `AI로 재현한 예상 모습`
- 공개 전단 연락처 전체 공개 + 사전 확인
- 112/182 제거
- 자체 제보 MVP 제외
- 작성자만 삭제
- Secret/PII 보안

**AI provider, 모델, prompt, AI 내부 파일/서비스 구조는 동결 대상이 아니다.**
